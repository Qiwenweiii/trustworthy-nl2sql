## 1. 评测目标

四条目标，逐条对照现状（核验依据是 `problems/eval_cases.json` 的 57 条用例断言）：

| 目标 | 现状 | 依据 |
|---|---|---|
| SQL 是否安全（只读、单条、有行数上限） | **已覆盖，且是 100% 确定性**：v0 8 条注入用例（S1/S2 + A1–A6 攻击面）走 `injected_sql`，不调模型、不花 key，可天天跑。但注意测的是「危险 SQL 进不了执行层」这条防线，**不是模型的守法率**——模型真写出写操作时，这些用例不会替它现形。 | 原 §2.1「安全」一条达成；攻击面用例见 §3 对照表第二行（已补） |
| 该拒答时是否拒答 | **已覆盖**：R1（区域）/R2（产品线毛利率）/R3（新客）三条，断言 `status_in=[no_sql]` + `sql_null` + `sql_not_matches`（禁止自造 `CASE WHEN` 映射、禁止窗口函数造口径）。v1 后期把判据从「模型自发拒答」升级成「语义层在调模型之前拦」，所以这三条现在是 0 次模型调用的确定性通过。 | `evaluation/NOTES.md` §2.6 机制拒答不计入不可靠清单 |
| 口径识别与澄清 | **测到的是「声明 + SQL 形状」，没有澄清**。K1/K2/K3 断言 `llm_response_matches` 里有口径字样、`sql_matches` 里出现 `status` 与逐行扣减的不含税写法；`sql_not_matches` 明确禁止 `SUM(amount) - SUM(tax_amount)` 这种整体相减的错公式。**没测**：口径歧义时是否反问——澄清本身没实现（v1 承诺文案已收窄为「口径声明（不含澄清）」），所以评测也无从测。 | 见 §2.1 与本文 §5 |
| 结果异常是否被标记而非静默输出 | **只覆盖空结果这一类**：E1/E2/E3 断言 `result_empty_or_null` + `llm_response_matches` 里要说破没数据。**负值、NULL 比例异常至今零用例、零断言**（指标登记表里也没有 `non_negative` 这类元数据可依据）。 | 原 §2.1「结果异常」只完成三分之一 |

**口径目标的一条重要区分**（容易读错）：K1/K3 的 `sql_matches` 断言要求 SQL 里出现逐行扣减写法（正则 `amount\s*-\s*(coalesce\(\s*)?tax_amount`），`sql_not_matches` 禁止整体相减（`sum(amount) - sum(tax_amount)`）。这是**评测层**的校验，错了报告里红一次；**运行层没有对应的公式注入或拦截**——`METRICS` 里的 `formula` 字段是只登记不执行的死数据。所以「口径公式写错」这件事只在评测报告里看得见，线上不会挡。

## 2. 评测维度

### 2.1 确定性断言 —— 已实现（12 种 check）

断言类型全部注册在 `evaluation/judge.py:301` 的 `CHECKS` 表里，每条形态都是 `check(expect) -> (passed, observed)`，`observed` 直接进报告当证据。完整表（expect 形状、拒答时是否跳过、实现行号）在 `evaluation/NOTES.md` §3，这里不重复。

三条影响用例可靠性的实现约定：

- **期望值只存在用例 JSON 里，Python 里不内联**。加用例只改 JSON，不改代码——破坏这条，用例就无法被他人复核。
- **容差必须在用例里显式声明**（`tolerance.mode` = `absolute` / `relative`），judge 不内置默认容差。
- **`result_value_in` 只比第一个数值单元格**，不认列名、不管行数。所以数值类用例都配了 `sql_matches` 先把 SQL 形状钉死（K1/K3 就是这么写的）。

### 2.2 Trace 行为断言 —— **换了实现路线，未按原设计做**

原设计（v1 后期）：断言工具调用序列是否符合预期（如先门控后生成）、错误路径是否记录明确信息。

**实际没有 trace 序列可断言**——链路不落盘、`outcome` 里也没有事件序列数组。拆成两个子目标，各自的下落：

| 原子目标 | 现状 |
|---|---|
| 「先门控后生成」的序列断言 | **没做断言，改成结构保证**：顺序硬编码在 `pipeline.ask()` 里（语义门 `:90` → 生成 → 指标注入 `:137` → 时间边界 `:151` → guard `:160` → 执行 `:173` → 判空 `:192`）。代码层面不可能出现「先生成后门控」，所以不需要断言；代价是这条保证在评测报告里是隐形的。 |
| 「错误路径记录明确信息」 | **做了**：`status` 六选一 + `error.type` 四选一（`semantic_refusal` / `sql_error` / `timeout` / `llm_error`），且评测报告**每次采样都原样保留** `guard` / `enforcement` / `time_fix` / `error` 四个痕迹字段。这解决的是原设计没提到的更要紧的问题——**分辨「模型自己写对」和「系统救回」**（K1 变绿到底是模型学会写半开区间，还是 `time_fix` 替它改的，读 `actions[].type` 就知道）。 |

**这条路线换来的代价，要如实记着**：报告 JSON 是运行产物（`problems/eval_report.json`，已进 `.gitignore`），历史快照靠人工复制到 `docs/`。没有 append-only 事件流，所以**跨版本回放某一次查询的完整过程做不到**，只能回放「本次采样的结论」。原立项文档里的 trace 设计（`TECH_DECISIONS.md` §3.3）仍是这项能力的唯一成文依据。

### 2.3 语义质量（v2，可选）—— 未做，也不建议先做

LLM-as-a-Judge 一条都没实现。理由不是省事：本项目已有的 57 条用例（含 v2 golden set 40 条）**全部是机器可判的确定性断言**，在数值口径都还没被运行层校验住之前，引入一个会抖的评审模型去判「答案完整性」，只会把「模型运气」伪装成「质量分数」。真要接，先补上 §5 里的负值/NULL 断言和 `caliber_note` 断言。

## 3. 数据集策略 —— **原「回归集 / 挑战集」二分被阶段制替代**

| 原设计 | 实际落地 |
|---|---|
| 回归集：日常调试用，覆盖核心场景，目标 15–20 条 | **按阶段分，不按「回归/挑战」分**：`--stage v0` = 8 条注入用例，不花 key、不受数据窗口抖动，等价于原「回归集」的日常角色。原「15–20 条问题分布」的目标由 **v2 golden set 40 条**（2026-11-06 入文件，状态 pending）承接：真实分布问法 + 锚定种子下的标准结果，度量执行准确率，不进日常门禁。 |
| 挑战集：发布前用，覆盖边界与攻击场景，目标 10 条 | 攻击面已补：A1–A6 六条注入用例（多语句+DROP、`ATTACH`、`PRAGMA`、注释藏关键字、WITH 后接 DELETE、`readfile`）进 v0 门禁，改坏 guard 评测报告现在会红。A4 是反向用例——注释里藏 `delete` **不该**被整体误杀，与 S2（只读函数 `replace()` 不该被误杀）成对，防门禁两头失真。边界类是 R1–R3（拒答）和 E1–E3（空结果），外加 v2 里的 D21/D22 缺口探针（曾测「城市取值未登记 → 语义层拒答」这一登记表缺口，基线里明知会红；城市取值已于 2026-11-06 登记进 `DIMENSIONS`，缺口已关闭，两条转绿由阶段 1 验收轮证明）。 |

**阶段制的额外收益**：`meta.stages.status`（done / pending）是 `--all` 退出码的**唯一数据源**，转阶段状态只改用例文件、不改代码。这条设计不在原骨架里，是把「阶段承诺」变成可执行门禁的关键——v1 于 2026-11-04 转 done 时做过翻转对照：同一条被人为改坏的 K1 断言，pending 时退出码 0、done 时退出码 1。

**v2 毕业标准（2026-11-06 裁决）**：golden set 不会永远挂在 pending，满足三条转 `done`——

1. **先补字典**：城市取值（上海/北京等）登记进 `DIMENSIONS`，让 D21/D22 探针自己转绿。不允许删探针或改期望值来凑全绿——这两条用例绿了本身就是"缺口被补上"的证据。**已完成**：2026-11-06（阶段 1 收口）八个城市取值登记进 `DIMENSIONS["城市"]["enum"]`，登记前先跑出 D21/D22 的预期红、登记后单测转绿；用例与期望值一字未动。
2. **连续两轮全绿，搭阶段 1 验收的车**：`--stage v2 --repeats 2` 连跑两轮，每轮 40/40 通过且同题每轮内每次采样都绿（不是蒙过一次）。时机定在**执行报错回炉（阶段 1）收口验收时**——验收轮直接充当毕业轮，不额外花考试钱（两轮合计约 160 次调用，本来就要跑）。
3. **翻转自证**：转 done 时按 v1 的惯例，故意改坏一条 v2 断言演示退出码 pending=0 → done=1，证明门禁真的咬人，不是纸面承诺。

毕业后：v2 失败与 v1 同性质，`--all` 退出码开始拦它，此后任何一条 golden 用例红都算回归。

**下一步补数据集的优先顺序**：① ~~注入攻击面~~ 已于 2026-11-06 落进 v0（A1–A6，零成本）；② 负值 / NULL 比例异常；③ 维度取值合法性（E3 现在只事后说破「没数据」，事前不拦；~~D21/D22 探针量化的「城市取值未登记」缺口~~ 已于 2026-11-06 登记城市取值关闭，「取值未登记就事前拒答」的通用规则仍待做）。

## 4. 执行与报告

| 原设计 | 实际 |
|---|---|
| 每次改 Prompt 或加功能后跑回归集 | **改成增量评测**：默认 `--ids <受影响用例> --repeats 1`，只跑相关用例并在汇报里注明调用次数。全量（`--all`，49 条真模型用例 × 默认 3 次 = 147 次调用，v1 9 条 + v2 golden 40 条都算在内）**由人决定何时跑**，不在日常流程里；日常零成本兜底是 `--stage v0`（8 条注入，0 次调用）。 |
| 输出通过/失败清单，失败项附 trace 摘要 | **三类结论：通过 / 失败 / 不可判定**（环境故障单独一类，不冤枉靶子）。失败按（类别, `root_cause`）聚合，同根因跨用例只列一组，每组带证据与「建议落点」。附的不是 trace 摘要而是**断言级 `observed` + 四个痕迹字段**。 |
| 版本对比：改前 vs 改后的通过率变化 | **换成两个更强的机制**：① 单测判别性——新测试必须先在修复前的实现上跑红、再复原跑绿；② 报告保留 `changed` / `actions[].type`，所以**通过率变化不再被直接当成质量提升的证据**（K1 三次全绿里有两次是 `boundary_rewritten` 救回、一次是模型自己换了字段，报告分得清）。原「比对通过率」这条从设计上就被判定为不可靠信号。 |

**两条防烧钱的入口约束**：`--stage` 与 `--all` 必须显式二选一，都不给或都给直接 `parser.error`（不给默认值，防止手滑一条命令烧掉上百次模型调用——扩到 57 条后全量默认是 147 次）；纯注入用例走 `load_config(require_llm=False)`，没有 key 也能跑。

报告格式与逐字段结构见 `evaluation/NOTES.md` §5；退出码规则见同文件 §4.7。
