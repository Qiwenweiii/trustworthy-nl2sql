# 阶段 3 工程方案 —— FastAPI 服务壳 + 问答前端

> 状态：**计划稿（未开工）**。开工前置条件：阶段 1 验收两轮落盘、毕业翻转完成（本文 §7 排期表写死）。
> 本方案的原则和管线一样：**先定契约，再动代码**——HTTP 层不发明新数据结构，前端不另开查询旁路。

## 1. 目标与非目标

**目标**（求职演示视角）：
- 给现有 `pipeline.ask()` 套一层最小可用的 HTTP 服务 + 一个问答式前端，让"自然语言 → 可信 SQL → 带证据的答案"能被任何人点开体验；
- 前端把管线已有的可信机制**展示出来**（透明证据面板、拒答补全、回炉痕迹），这是和"套壳 NL2SQL demo"拉开差距的地方；
- 收口时能产出台账要的数：端到端延迟分位数、演示用例通过率、接口契约测试覆盖。

**非目标**（明确不做，防止范围膨胀）：
- 不做用户体系、会话持久化、多轮上下文——单轮问答，聊天记录放浏览器内存；
- 不做表单查询模式（2026-11-06 讨论已否：绕过拒答/注入/回炉整条可信链路）；
- 不改 `outcome` 字段字典——前端需要的一切从现有字段和 `/api/meta` 推导；
- 不做鉴权、部署上线（本地 uvicorn 即演示形态）；图表可视化放 v1.1。

## 2. 架构总览

```
浏览器 (Vite+React, localhost:5173)
   │  fetch POST /api/ask {question} —— SSE 事件流（阶段进度 + 终局 outcome）   fetch GET /api/meta
   ▼                                        ▼
FastAPI 壳 (uvicorn, localhost:8000)  ←—— web/server/（新目录，不进 src/data_agent）
   │  只做三件事：入参校验、调用、回 JSON
   ▼
pipeline.ask(question, ...)        ←—— 一行不改。CLI/评测/Web 三个入口共用同一管线
   │
   ├─ data/web_demo.db（demo.db 的只读副本，见 §4.3）
   └─ OpenAI 兼容 API（模型 key 沿用 .env，配置只有一份）
```

分层逻辑：`web/server/` 是**薄壳**，允许的业务逻辑只有"参数白名单 + 并发闸门 + 配额计数"；一切数据正确性由管线内部保证（guard/enforcement/time_fix/retry 照常运转）。这样评测结论对 Web 路径同样成立——Web 只是第四个调用方。

## 3. 后端契约（FastAPI）

### 3.1 接口清单

| 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `POST /api/ask` | `{question: str}`（1–200 字符，去空后非空） | **SSE 事件流**：`stage` 事件（阶段名+耗时，见 §4.3）若干条 + 终局 `result` 事件（**outcome 原样透传**，README/outcome 字段字典那 16 个键，一个不加一个不减） | 主接口。业务成败看终局帧的 `status`，事件流只负责"直播系统在干嘛"，不承载新契约 |
| `GET /api/meta` | 无 | `{metrics: [{name, synonyms}], dimensions: [{name, aliases, enum?, column}], sample_questions: [str]}` | 前端 chips/补全按钮/推荐问法的数据源。**全部从 `semantic_tables` 现读**，和评测探针、拒答文案是同一份字典，不手抄 |
| `GET /api/health` | 无 | `{ok, db_exists, config_ok}` | 起服务自检：库在不在、key 配没配，缺了给明确文案（沿用 `ConfigError` 那套"退出码 2"语言） |

**不暴露的参数**：`injected_sql`（评测专用后门，Web 上暴露等于绕过模型+guard 的攻击面）、`today`、`max_rows`、`timeout_s`——一律用 Config 默认值。这是接口层的白名单纪律，要写进测试。

### 3.2 保护性设计（壳层仅有的三行逻辑）

- **并发闸门**：进程内信号量，同时最多 2 个 `/api/ask` 在执行（一次请求背后是一次真实模型调用，放开并发等于给同事演示时手滑烧配额）；满了返回 429 + `{"detail": "演示服务并发已满，请稍后再试"}`。
- **日配额计数**：进程内计数器，默认上限 300 次/进程（环境变量可调），演示场景够用且不失控。
- **异常兜底**：管线内部已把 LLM/DB 异常收敛成 `llm_error`/`exec_error` 状态；壳层只兜"理论不该发生"的未知异常 → 500 + 固定文案，不泄漏堆栈。

### 3.3 依赖与目录

```
web/
  server/
    __init__.py
    app.py            # create_app(cfg) -> FastAPI；路由薄壳
    schemas.py        # /api/ask 入参校验模型（pydantic）
  run.py              # 启动入口：uvicorn web.server.app:build_app --factory
frontend/             # 见 §4
```

`pyproject.toml` 增加可选依赖组 `web = ["fastapi>=0.110", "uvicorn>=0.29"]`——放**可选组**而不是主依赖，评测/CLI 用户的安装面不被前端拖着变大。安装动作排到验收轮落盘之后（§7）。

## 4. 前端

### 4.1 选型：Vite + React + TypeScript

理由：组件化对得上 §4.2 的卡片结构；求职叙事后端已经是 Python，前端用主流框架补齐"全栈能独立起 demo"的故事；成本可控（一个页面、四个组件）。若想要零构建的备选：单文件 HTML+JS（mockup 即雏形），牺牲组件化换更小的工程面——**默认走 React，被问起时讲得出这个取舍**。

### 4.2 组件与交互（对 `datagent-chat-mockup.html` 逐项实现）

| 组件 | 数据来源（全部现有字段，不加契约） | 交互要点 |
|---|---|---|
| `ChatThread` | 本地状态 + `stage` 事件 | 用户气泡 + 助手卡片流；等待期展示分档进度文案（设计见 §4.3，不是静态转圈） |
| `AnswerCard` | `status=ok`：`result.rows/columns/row_count/truncated/max_rows`、`caliber_note`、`llm_response` | 结论大数字取首行首列；`empty_result=true` 走空结果样式（提示"当前条件下没有数据"是管线写的原文，前端不另编）；`truncated` 显示"被上限截断"角标 |
| `EvidencePanel`（折叠） | `sql`、`guard`、`enforcement.actions[]`、`time_fix.actions[]`、`retry` | 高亮靠 from→to 对照渲染：`conflict_replaced`/`boundary_rewritten` 拿 `from`/`to` 两个串做 diff；`added` 直接列补写条件；`retry` 展示 `failed_sql`+`db_error`+`regenerated_sql` 三段；`guard.passed=false`（blocked）时整卡变拦截样式 |
| `RefusalCard` | `error.type=semantic_refusal`：`error.message` + `/api/meta` | 缺指标 → 渲染 `meta.metrics` 按钮；缺维度取值（文案含"不是…已登记的取值"类）→ 渲染该维度 `enum` 按钮；点击**回填输入框**并标记原卡已补全。判定用 message 前缀匹配即可，规则简单且写死在前端——这是"澄清做成 UI affordance、不动管线"的代价，明确记录 |
| `QuickChips` / 补全 chips | `/api/meta.sample_questions`（后端从 v2 golden set 里挑 8–10 条真实问法） | 点一下填输入框，不直接提交 |

拒答路径零模型调用（语义层拦在模型前），补全体验必须是**秒回**的——这点是前端最能体现管线价值的地方。

### 4.3 等待体验：查询不是秒回的，等待要摊开讲

延迟账先算清（三档，来自实测）：

| 档 | 场景 | 时长 | 体验策略 |
|---|---|---|---|
| 秒回档 | 拒答、补全 chips、/api/meta | 毫秒级（没调模型） | 立即出卡——这是最能体现"拦在模型前"价值的瞬间 |
| 正常档 | 生成 + 校验 + 执行 | ≈10–25 秒（评测实测均值 ≈24 秒/调用） | 阶段直播 |
| 回炉档 | 首稿执行报错 → 修复重跑全链 | ≈50 秒起 | 阶段直播 + 明示"为什么多等" |
| 理论天花板 | LLM 超时 60s×2 + 查询超时 5s×2 | ≈130 秒 | 超时兜底文案，绝不装死 |

设计原则：**等待时说的话，必须和最后证据面板里记的账同源**——直播"系统补写口径条件"和终局 `enforcement.actions` 是同一步的两个时态，不会出现"直播说的和成绩单不一样"。

- **SSE 事件粒度**：`拒答判定` → `生成 SQL` → `静态安检` → `口径注入/边界修正`（有动作才发）→ `执行` → （触发时）`首稿报错，回炉修复` → `完成`。每帧带阶段名与已耗时。
- **前端分档文案**：0–5s 骨架屏"正在理解问题…"；之后直接渲染 SSE 推来的真实阶段名（"系统正在核对口径"这类话本身就是产品教育）；回炉事件出现时展示 mockup ③ 那句「首版 SQL 执行失败，已送回修复」——把慢的原因摊开，等待就从"卡住了"变成"它在干活"。
- **防等待被浪费**：请求期间该会话输入禁用重复提交（闸门 429 是第二道保险）；SSE 断流自动降级为"结果仍在生成，稍后回来看"，不做持久化恢复（超范围）。
- **M1 验证项（写死）**：核对 `pipeline.ask()` 的可选入参能否向壳层透传"步到步"的回调（管线内部三本账已有记录点）。**透传不了就降级**：壳层只发粗粒度帧（开始/完成），前端按计时器切通用文案，且不谎称真实步骤——降级与否在 M1 结论里记录。

### 4.4 数据库隔离

Web 起服务时 `DATA_AGENT_DB_PATH=data/web_demo.db`（demo.db 的文件副本，`init_db` 同锚点生成，`.gitignore` 收掉）。目的：演示点击与评测跑批**物理隔离**，演示写坏/锁库都碰不到正在考试的库；前端形态也不需要写路径（管线本来就只读）。

## 5. 测试方案（沿用项目判别性纪律）

- `tests/test_web_api.py`（pytest + `fastapi.testclient.TestClient`，替身 generator 注入，不花 key）：
  1. 契约透传：替身管线返回完整 outcome → SSE 终局 `result` 帧的键集合与 outcome 字段字典**逐键相等**（多一个键、少一个键都红）；`stage` 帧只含阶段名与耗时，**不携带任何 outcome 数据**（直播不夹带私货，红测试先写在不过滤的版本上）；
  2. 参数白名单：请求体塞 `injected_sql`/`max_rows` → 被 422/忽略，**断言替身管线收到的 kwargs 里没有这些键**（先在不过滤的版本上跑红再实现，判别性流程）；
  3. 并发闸门：第 3 个并发请求拿到 429；配额打满后拿到 429；
  4. `/api/meta` 与 `semantic_tables` 一致性：返回的指标名/维度 enum 就是登记表本身（登记表加一条，meta 自动多一条，测试断言同源）；
  5. 异常兜底：替身管线抛未知异常 → 500 + 固定文案，不含堆栈字样。
- `tests/test_web_smoke.py`：起 app factory 不连库不连模型，health 给出可诊断的缺配置文案。
- 前端不铺单测（范围控制）；收口交付按"端到端手跑演示"标准：正常/拒答补全/回炉/空结果四条真实链路各演示一次（对齐既有交付习惯）。
