## 这个项目要做什么

一个能回答数据问题的 Agent。用户在自然语言里问一个数据问题，系统理解它、生成 SQL、查数据库、返回结果。

但和普通的 NL2SQL 工具有一个关键区别：**系统在"不确定"的时候会先问清楚，而不是瞎猜一个数给用户。**

具体来说，它要做四件事：

### 1. 听懂问题，先检查口径

用户问"上个月销售额是多少"。

系统先查自己的指标定义表，发现"销售额"有含税、不含税两种口径，用户没说清楚。

这时候系统**不查数据库**，直接回一句：

> 销售额有含税/不含税两种口径，你要哪个？

用户选了之后，再往下走。

如果用户问的是"上个月不含税销售额"，口径唯一，直接往下走，不需要澄清。

如果用户问的东西在指标定义表里找不到，系统返回"未识别到指标"，**不猜测**。

### 2. 生成 SQL，查库

口径确认后，调用大模型生成 SQL。对 SQL 有硬性限制：

- 只允许单条 SELECT 语句；
- 自动加返回行数上限；
- 执行有超时，超时就中断；
- 数据库连接是只读的。

查完拿到结果，进入下一步。

### 3. 检查结果正不正常（这一步不能偷懒）

拿到结果后，**不用同一套 SQL 再跑一遍来"验证"**——那等于自己批自己的卷子，只能证明执行是确定性的，证明不了口径对。

系统用另一套独立规则看结果结构：

- 结果是不是空的？
- 关键字段是不是大面积没值（NULL 比例过高）？
- 销售额这种不该为负的指标，是不是出现了负数？

有问题就在答案里明确标出来，不能装作没看见。

这里有一个硬性约束：**检查逻辑不得调用 SQL 生成/执行模块，不得重跑同一 SQL，不得复用计算函数。** 它只看"结果长什么样"和"指标定义"，不看"怎么算出来的"。

### 4. 给答案，带上证据

最终回答不只是一个数字，而是一份带证据的答复，至少包含四项：

- 用的是哪个口径；
- 数据来自哪张表；
- 生成的 SQL 是什么；
- 校验结论是什么（正常 / 有异常 / 无法可靠回答）。

示例：

> 上个月不含税销售额是 123 万。
> 口径：不含税，按支付时间；
> 来源表：fct_sales；
> SQL：（附）；
> 校验：正常。

如果结果异常、或者口径一直没确认，系统不硬给一个数，而是说：

> 当前无法可靠回答，原因是……

## 用户会怎么用

- 正常情况：用户问 → 系统出数 → 返回带证据的答案。
- 口径歧义：用户问 → 系统反问口径 → 用户选择 → 系统继续出数。
- 无法识别：用户问 → 系统说"没识别到这个指标"。
- 结果异常：用户问 → 系统查出异常结果 → 答案里标出异常，或者拒答。

## 第一阶段：最小可用版本

先做一个能跑的版本，不带可信层。它只有一条管道：问题 → 生成 SQL → 查库 → 返回结果。

**这一阶段不做的**：

- 不做口径检查；
- 不做结果校验；
- 不做证据组装；
- 不做步骤展示。

**第一阶段完成的标志**：

- 能对 5–10 个预设问题生成 SQL 并返回结果；
- 非 SELECT 语句被拦截；
- 有一个演示数据库和几条样例数据；
- 能跑通一条完整链路。

## 第二阶段：可信改造

第一阶段跑通之后，往上加可信层。每一层都要有明确的"改前 vs 改后"对比：

| 改造     | 改前                       | 改后                             |
| -------- | -------------------------- | -------------------------------- |
| 口径门控 | 用户说"销售额"直接生成 SQL | 发现多口径，先问"含税还是不含税" |
| 结果校验 | 跑出什么返回什么           | 空结果 / 负值 / NULL 异常被标记  |
| 证据展示 | 只返回最终数字             | 返回口径、SQL、来源表、校验结论  |
| 拒答     | 永远给答案                 | 不确定时明确说"无法可靠回答"     |

## 明确不做的

- 多数据源接入；
- 向量检索和复杂 RAG；
- 用户系统、权限体系；
- 完整前端界面（能用接口或最简页面演示即可）；
- 追求 NL2SQL 基准准确率；
- 生产级高可用和横向扩展。
